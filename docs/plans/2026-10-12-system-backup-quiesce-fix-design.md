# 系统备份快照等待热修复设计

## 问题

线上首次真实导出在快照进度 8% 失败，错误为 `Timed out waiting for scheduled writes to finish`。失败时没有开始压缩或加密，也没有产生可下载的残缺备份。根因是当前流程先开启全局维护门，再停止调度器并等待在途任务；经营分析物化、仓库或妙手同步单次可能超过固定的 120 秒，因此备份会失败，同时等待期间还会不必要地拒绝业务写入。

## 方案比较

1. 只延长维护超时：改动最小，但会让业务写入在整个后台等待阶段持续收到 503，不采用。
2. 后台任务未结束时直接复制：导出速度快，但 SQLite、JSON 和附件之间可能不是同一业务时点，不符合一致性备份目标，不采用。
3. 先静默调度、后进入短维护窗口：停止产生新的后台任务，但允许正常业务继续使用；等待已在途任务完成后，再短暂停止新写入、排空当前写请求并复制快照。采用此方案。

## 数据流与错误处理

导出任务进入 `waiting_background_tasks` 阶段后停止调度器和协同桥接定时器，在维护门之外等待调度器、协同桥接和应用内后台写入收尾。页面持续显示正在等待的任务名称，并明确此时业务仍可正常使用。等待上限独立配置为 `SYSTEM_BACKUP_QUIESCE_TIMEOUT_MS`，默认 2 小时，以覆盖线上已观测到约 62 分钟的第三方同步，同时避免永久挂起。

后台空闲后才进入 `draining_writes`：维护门阻止新的 POST、PUT、PATCH、DELETE，请求排空后再次确认后台空闲，然后复制 `.cache` 与 `.env`。无论成功或失败，都先释放维护门，再恢复后台调度。超时错误改为中文并带出仍在运行的任务名称，便于排查。

## 验证

回归测试模拟一个超过旧 120 秒逻辑比例的慢任务（测试中使用短延时），断言等待期间维护门未开启且普通写入仍被允许；任务完成后只在复制窗口进入维护状态。继续执行加密归档、恢复事务、权限、生产构建和 API 冒烟测试。线上发布后核对新提交、PM2、恢复代理心跳和备份任务状态，再由管理员从页面重试真实导出。
