## 一、结论

经营贡献的聚合程序在同一批事实明细内能够正确加总，按日、周、月、国家、仓库和品牌拆分后与总计相符，差异仅有人民币 0.01 元以内的展示舍入误差。国家直营成本匹配、汇率换算和打包费规则也已按设计工作。

但当前数据仍不能作为完整经营利润结论，主要因为：

1. 妙手交易同步在同步当天数据时，把结束时间固定为当天 `23:59:59`，妙手拒绝晚于当前时间的参数，导致同步失败；经营贡献实际继续使用 WMS 销售数据。
2. 默认近 90 天页面的销售额覆盖率仅 27.4%、成本覆盖率 30.8%、利润覆盖率 25.0%，俄罗斯订单基本只有数量和成本，没有有效销售额。
3. 页面“覆盖范围销售成本”和“覆盖范围预估毛利”并非同一覆盖样本：成本汇总包含所有已知成本，毛利只统计收入、产品成本和打包费同时完整的行。因此页面上的“销售额－销售成本”不会等于“预估毛利”。这是口径表达问题，不是单行减法错误，但会明显误导用户。
4. 后台物化已成功移出请求线程，页面不再因 5 万多毫秒的重算而完全卡死；但筛选仍需在主线程扫描约 8.8 万行并返回约 0.5 MB 数据，当前实际筛选耗时约 0.33–3.33 秒。

综合判定：**聚合一致性通过；数据完整性、利润可解释性和正式经营结论未通过；性能改造部分通过。**

### 4. 妙手同步失败根因

同步状态最后错误为：`订单修改时间结束时间不能晚于当前时间`。

代码对包含今天的同步窗口固定生成：

- `gmtModifiedTo = 当天 23:59:59`；
- 售后接口 `gmtStartTo = 当天 23:59:59`。

在当天 23:59:59 以前运行，结束时间一定晚于当前时间，妙手拒绝请求。代码同时使用 UTC 日期生成“今天”，也存在服务器时区与妙手业务时区错日风险。

## 五、成本口径验证

产品成本已按“SKU + 国家”优先匹配对应国家的直营成本价；只有不存在国家明细时才回退到无国家的基础产品成本。产品成本按订单日期对应汇率折算成人民币。

打包费按订单总件数计算后，再按每个 SKU 行的件数占比分摊。四国规则与需求一致，当前规则覆盖率 100%。

现有利润公式的单行计算正确：

`覆盖样本预估毛利 = 有效销售额 - 对应产品成本 - 对应打包费`

问题出在汇总展示：总销售成本会累计收入缺失行的已知成本，而预估毛利只累计完整行，导致页面三张 KPI 卡片不是同一统计集合。

## 七、修复与防复发建议

### P0：先恢复真实收入源并修正利润口径

1. 对包含今天的妙手同步窗口，将 `gmtModifiedTo` 和 `gmtStartTo` 截断为当前业务时区时间；历史日期仍使用 `23:59:59`。统一使用明确的妙手业务时区，不再用 `toISOString().slice(0, 10)` 判断本地“今天”。
2. 修复后执行 90 天回补；只有订单匹配率达到 98%、金额分摊误差为 0、仓库快照完整时，才允许妙手从影子源切换为正式销售额源。
3. 新增同覆盖口径：`profitCoveredSalesCny`、`profitCoveredCogsCny`、`estimatedProfitCny`。三项必须来自完全相同的明细集合。
4. 当前 `cogsCny` 改名为“已识别成本”，避免与覆盖样本毛利并排造成减法误解。利润覆盖率低于 95% 时，标题使用“覆盖样本毛利”，不得显示成完整货盘预估利润。

### P1：补齐数据并加速筛选

1. 建立缺失 SKU、品牌、国家直营成本的异常清单和负责人闭环；优先处理 8,919 行未匹配产品和 16,250 行成本缺失。
2. 将经营贡献筛选、聚合改为数据库 SQL 聚合，并为日期、国家、仓库、平台、店铺、项目组、品牌、SKU 建组合索引；必要时维护日粒度预聚合表。
3. 拆分接口：KPI/趋势、品牌、产品、筛选选项分别加载；产品列表分页；不要每次返回全部产品、品牌、近期明细和全部筛选选项。
4. 前端对连续筛选请求做防抖和取消旧请求；店铺改为可搜索、虚拟滚动选择器，不一次性渲染 243 个原生选项。
5. 数据未就绪时保留上一份“完整正式快照”，并在页面同时显示“正式快照截止时间”和“后台增量同步进度”。

## 八、上线建议

当前版本可以继续作为“暂估分析与数据修复工作台”使用，但不应作为正式利润结算或绩效考核依据。完成 P0、回补数据并连续三次自动验收通过后，再把状态从“暂估数据”升级为“正式数据”。

## 九、2026-09-03 修复实施记录

本次已完成代码修复并通过本地回归，尚待发布到线上后执行妙手历史回补与生产数据复验：

4. 筛选聚合迁移到独立 Worker，不再占用 API 主线程；日期先二分截取，再按权限和筛选条件聚合。
5. 接口限制为产品榜单最多 100 条、近期事实最多 50 条，同时返回完整结果总数，避免页面误认为只存在 100 个产品。
6. 前后端默认日期均按业务/浏览器本地日期生成，消除北京时间凌晨被 UTC 日期错分到前一天的问题。
7. 代表性本地快照（83,471 行）实测：Worker 首次初始化加查询 931 ms，预热后 97 ms（其中聚合 96 ms）；响应约 283 KB，返回产品 100/178、近期明细 50 条。该结果需在线上相同数据量下再次验证 P95。
