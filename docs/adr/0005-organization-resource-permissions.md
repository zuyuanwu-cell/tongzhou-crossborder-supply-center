# ADR 0005：组织资源范围与业务能力授权

- 状态：已接受
- 日期：2026-09-28

## 背景

外部协同门户已经按 `organization_id` 隔离组织，但同一组织仍可能只负责部分仓库或部分 OEM 协同能力。仅依赖成员角色无法表达“某组织只能处理 A 仓、且只能确认入库”的边界，也无法阻止错误投影被发布给未授权组织。

## 决策

有效权限由三层共同决定：组织资源授权、组织业务能力、成员角色。任意一层不满足都拒绝请求。

- 内部中台管理员分配资源范围和业务能力；外部组织管理员不能扩大该范围。
- 仓库组织按 `warehouse_ref` 授权，可同时拥有多个仓库；OEM 组织按其唯一业务空间授权。
- 协同 API 在投影写入、列表、详情、动作、附件和 OEM 提交处校验授权。
- PostgreSQL RLS 继续承担组织级隔离；资源授权承担组织内最小范围隔离。两者不能互相替代。
- 新组织默认无资源授权。迁移仅为已有投影推导授权，避免破坏存量协作。
- 授权变更整体替换并写入追加式审计日志，便于追踪谁在何时授予或撤销了什么。

## 备选方案

1. 只在前端隐藏入口：无法阻止直接调用 API，否决。
2. 将仓库写入成员权限：多人维护容易漂移，且组织新增成员时容易越权，否决。
3. 每个仓库固定一个组织：首期简单，但无法覆盖同一服务商管理多仓，保留为运营建议而非技术限制。
4. 为每种业务建立独立权限表：约束更强但扩展成本高，当前采用统一授权表加严格目录校验。

## 影响与故障处理

- 授权缺失时投影返回 `403 resource_not_granted`，不会落入伙伴可见主表。
- 撤销授权后数据不删除，但门户立即不可见；恢复授权后历史可继续追溯。
- 核心系统仍是真值源，授权不会使协作库成为库存或合同主账。
- 若 API 查询遗漏资源过滤，RLS 仍能阻止跨组织访问；自动化测试覆盖同组织跨仓越权。
